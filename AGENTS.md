# Container benchmark

This project owns isolated protocol interoperability, Vole native-TUN pressure, and matched Vole/Mihomo comparisons. Read `README.md` before changing workloads, cases, metrics or cleanup.

## Test authorization and isolation

- The user's task authorizes the requested interoperability, regression, performance and defect-diagnosis work within our owned test lab. Use synthetic traffic and test identities; this scope does not authorize testing unrelated systems or production/user traffic.
- Keep protocol servers, origins, reference clients and network workloads inside owned containers and isolated namespaces. Use the lab's NAT network without publishing host ports. The host runs orchestration, compilation and offline analysis; preserve its VPN, routes, DNS and firewall, and preserve unrelated resources.
- Direct test traffic only to the owned lab peers and origins for the requested cases, rates, concurrency and duration. Official dependencies, release binaries, rule data and documentation may be fetched as inputs; those public services are not load-test targets.
- Packet captures, TLS session keylogs and decryption are limited to our own synthetic test sessions and keys. Collect only what the diagnosis needs, keep secrets out of task briefs and retained reports, retain no raw traffic in conclusions, and apply the cleanup rules below to these temporary artifacts.
- Every delegated subtask, including nested delegation, must explicitly state its goal, permitted actions/files, excluded actions, test environment, owned targets/resources, applicable data and key limits, host isolation boundaries, and resource/cleanup owner. Include these boundaries in the task brief rather than relying on inherited context. For offline-only work, state whether lab captures/session keys are needed and exclude network execution and new test resources. Delegation does not expand the user's authorized scope.

## Benchmark workflow

- Supply Vole explicitly through `--source vole=PATH`; never infer a parent/sibling checkout. `interop --list` is offline and source-free. Production compilation and Rust memory/configuration regressions remain in Vole.
- Keep `interop`, `stress` and `compare` outcomes separate and share one workload/observer. Vole and Mihomo are the only comparison clients. Retain and compare actual throughput, CPU, RSS and packet loss when Mihomo has compatibility errors with either a Mihomo listener or an official server; record integrity errors separately. Follow the measurement and acceptance rules in `README.md` under “优化与验收策略”. Adapters prepare normal binaries, configuration and startup.
- Select servers by support for the exact protocol and field: VLESS uses Mihomo, then Xray-core, then v2ray-core; VMess uses Mihomo, then v2ray-core; SS2022 uses Mihomo, then shadowsocks-rust, then Xray-core; Trojan uses Mihomo, then Xray-core; TUIC v5 uses official Itsusinn/tuic, with Mihomo only for its documented UoT v2 and server-side mTLS client-certificate authentication gaps; other protocols use Mihomo, then their official server. Apply the field evidence in `docs/server-selection.md`. For the explicitly authorized Mieru listener defects in `docs/server-selection.md`, use the official server with defect evidence and separate peer-specific PASS history. Otherwise a later server requires official documentation or source establishing that an earlier server does not support the required inbound field. All other handshake, interoperability or performance failures stay on the selected server for diagnosis. If no permitted peer supports a case, record that validation gap instead of substituting a different wire behavior.
- Route every network validation workload through a real TUN, including CLI, native Invoke/FFI, protocol, DNS, lifecycle and performance checks. Reuse the Linux raw-IP TUN and isolated client namespace; verify actual TUN traffic and cleanup. Controller requests remain management traffic. Offline checks and compilation do not require a TUN.
- Run owned containers on the same latest official Ubuntu LTS image and NAT. Dedicated build containers use 5 CPUs and 16 GiB; runtime peers, origins and load clients use 5 CPUs and 8 GiB. For performance runs, use the shared TUN/eth0 queue profile in `README.md` for both cores; retain other core defaults and leave origin queues unchanged. Disclose representation and routing differences.
- Freeze official MetaCubeX/meta-rules-dat complete (non-lite) `geosite.dat` and `geoip.dat` at one source revision for each performance or memory-pressure comparison. Load complete `geosite:cn` and `geoip:cn`; change categories only on an explicit user request. Source any added MRS, MMDB, DB, MetaDB or ASN input from the same official repository and record its fixed identity.
- Check stable public dependencies once per local day in the ignored cache; freeze identities per session. Stop builders before load and record actual binary/source/rule identities.
- Keep actual throughput, CPU, RSS, directional UDP delivery and DNS completion separate. Mark unavailable data explicitly; measurements are not release or device acceptance.
- For pressure batching, checkpoint gates, saved-window continuation and shared-layer regressions, follow `docs/batch-orchestration.md`; apply the source-comparison and profiling sequence in `README.md` under “优化与验收策略” before performance or defect fixes.
- Keep verified shared dependencies in ignored `.cache/`, per-run inputs/builds/logs in `.work/`, and text conclusions in `conclusions/`. Stop, join and delete exact owned containers; save conclusions before deleting scratch. Preserve unrelated resources and source checkouts. Keep scratch for recovery when cleanup or conclusion persistence fails.
- Run focused offline tests for code changes. Execute only the requested container smoke/matrix; offline/list results, interop, performance and physical-device/release acceptance are distinct evidence.
