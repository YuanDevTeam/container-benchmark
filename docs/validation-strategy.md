# 验证场景与验收口径

所有网络业务始终使用隔离Linux容器中的真实raw-IP TUN，保留Controller、完整官方CN GeoData、正常CLI与既定服务端选择。当前默认只使用1 Gbps，2／3 Gbps、平台和真机验证继续暂缓。以下是场景选择和结果解释合同，不表示新增场景已经运行或通过；历史输入、FAIL／ERROR和通过清单保留原身份，不追溯改签。

## 场景分层

| 层次 | 主要问题 | 覆盖与判据 |
| --- | --- | --- |
| 基础互通与有限交付 | 配置能否握手、收发和正确结束 | 全部组合使用适度负载和有限数据，校验内容、来源、实际完整交付、半关闭、Stop和清理；不套用定速性能参考 |
| 日常与少量慢连接 | 正常任务是否被少量慢任务拖慢 | 复用`experience daily`、`mixed-slow`的代表路径，保留任务成功数、正常任务耗时、慢读隔离、恢复和内存；不扩成所有变体的笛卡尔积 |
| 持续负载 | 固定应用供给下的实际性能 | 代表组合分别测纯TCP、纯UDP和混合流；保留60秒活动窗口、吞吐、CPU、RSS和交付丢包，性能与完整性独立判读 |
| 极端压力 | 高关联数、密集DNS、慢读是否造成失控 | 选择少量专项，先区分变量，再按需叠加；观察内存、存活、正常连接隔离和压力回落后的恢复，保留实际容量不足 |
| 长期运行与恢复 | 长连接、空闲、重连和突发后是否累积资源 | 少量代表路径延长观察并包含升载、回落、恢复；时长与节奏在执行前明确，不给全部矩阵统一增加长跑窗口 |

代表组合按独立协议／传输实现和受影响路径选择。只改变配置字段、但不改变关键数据路径的变体，完整互通仍独立保留，性能验证可共用有明确依据的代表；不能因名称相近就合并不同编码、复用、拥塞控制或H2/H3实现。公共层影响与独立协议影响分别登记，测过的旧PASS不代签新实现。

现有批量定速负载保持原输入，作为高关联数与DNS叠加压力。后续若需要单目标／少目标容量窗口、较低速率诊断或独立DNS专项，应另列输入身份和代表选择，不暗改当前64流、目标轮转或DNS负载，也不清空历史容量FAIL。验证范围不自动扩展为“全部组合×全部场景”。

现有`experience`中的`single-tcp`观察单流容量；`daily`与`mixed-slow`是约104 Mbps的有限任务，正常任务包含人为发送节奏，其P95不是网页首字节延迟。它们主要复用持续连接，不能代签频繁建立新连接的体验。高并发专项维持暂缓，历史超内存门槛的FAIL保留，已有结果按[结果总览](benchmark.md)的实际范围解释。

## 性能参考与独立必要门禁

| 结论 | 关注内容 | 与其他结论的关系 |
| --- | --- | --- |
| 完整性 `integrity` | 错误内容、错误来源，以及TCP实际已发送字节／摘要／结束状态的期限内一致性 | UDP丢包另列，不要求UDP零丢包；TCP配额不足不等于已发送字节缺失；证据不足记`UNKNOWN` |
| 性能参考 `performance_reference` | 1 Gbps活动窗口实际吞吐≥950 Mbps、适用的UDP交付丢包≤1% | 两个适用指标达到即性能PASS，停止该项性能优化；纯TCP不适用UDP指标，CPU只记录 |
| Mihomo匹配对照 `reference_acceptance` | 初期吞吐≥min(950 Mbps,Mihomo实测)，UDP丢包≤max(1%,Mihomo实测)；多轮结束后按下述相对10%阶段 | 达到适用目标即性能PASS并停止该项性能优化；Vole自身完整性、内存、真实测量、DNS、正常Stop和清理要求保持 |

每个精确窗口优先达到或优于匹配Mihomo，独立生产候选优化最多20轮。真实TUN有实际代码候选及闭合负载结果才计轮；对照／重复、纯观测和仅编译／内存检查不算新轮。经多轮仍未达到时可记录原因提前结束，20轮则停止继续追优，不为凑数延长。

阶段结束后允许最高**相对10%**差距：吞吐≥min(950 Mbps,0.9×Mihomo实测)，UDP丢包≤max(1%,min(100%,1.1×Mihomo实测))。服务端与窗口／TLS／速率／负载范围必须与实际候选、闭合结果和结束说明一致；未取得这些依据或范围不符时保持初期标准，记录严格结果、实际轮次、结束原因及降级阶段。CPU继续记录。内存、完整性、真实负载、DNS、测量、Stop／清理不放宽，历史FAIL／ERROR与原证明不改写。

内存继续是综合验收必要门槛：**1 Gbps≤43 MiB，后续2／3 Gbps≤45 MiB**，边界包含等值，不按系统或构建切换。Linux CLI生命周期RSS只作筛查，iOS／tvOS整个VPN扩展的physical footprint仍须独立测量，不能从Linux通过推导真机通过。

当前不设置绝对容量轴或990 Mbps／0.2%的硬门槛。`performance_reference`按实际窗口和收发证据给出`PASS`／`FAIL`／`UNKNOWN`／`NOT_APPLICABLE`，记录`basis`为`default`、`mihomo`或`mihomo-fallback-10pct`及逐指标目标、实测值；降级阶段另保留严格判定和轮次证据。错误内容仍计入raw吞吐，不把坏内容吞吐冒称正确交付；性能通过不豁免完整性、内存或测量失败，也不因后者失败把性能状态改写成FAIL。若只剩实际TCP缺口，后续只处理交付，不继续追逐吞吐。

新`pressure_met`为默认950 Mbps／1%性能参考和独立必要门禁的综合判定；匹配Mihomo的`reference_acceptance`另保留综合状态及`performance_status`。`UNKNOWN`或未执行不补PASS，UDP全无接收也不能宣称内容与来源已经验证。原始`data_valid`、`load_reached`、case状态和历史`pressure_met`／`absolute_capacity`结论不改写；旧990 Mbps／0.2%及绝对容量只代表当时标准，不迁移历史FAIL／ERROR或通过清单。后续证明保存当前性能与完整性，不新增绝对容量字段。

`load_reached`含原99%吞吐复合门槛，因此950–990 Mbps时的原始false不能证明实际负载窗无效。当前测量门禁按完整活动窗口、实际收发计数、正常进程/TUN和DNS等独立证据判断，不用改写raw字段适配新参考值。

结果的`validation_layer`区分现有日常／单流场景、`compound-pressure`组合压力及`interoperability`互通。日常和单流基线不额外引入定速性能门槛，性能参考记`NOT_APPLICABLE`，实际吞吐仍保留。检查点及后续通过证明分别显示完整性、性能、内存和测量状态，原记录不迁移。

后续2／3 Gbps仍沿用既定过载口径：允许断连、丢包和有界队列保护内存，但必须保持已接收内容与来源正确、完整负载观察及正常Stop／清理。实际TCP截断和未完成量照实保留，不强套1 Gbps的容量或完整交付门槛，也不能将过载内存通过写成无错误容量通过。

Mihomo即使与listener或官方服务端存在兼容错误，仍统计其实际吞吐、CPU、RSS和丢包作为本次匹配对照；完整性错误独立保留。吞吐包含错误数据和错误返回前的部分I/O；历史字段`goodput_mbps`沿用名称，表示活动窗口raw接收吞吐，不表示正确交付速率。UDP丢包仍使用实际发送与唯一有效接收量，坏包和重复包不会抵消交付缺口。Vole自身错误内容或来源不能获得综合通过，不能引用Mihomo错误豁免。

准备失败、进程观测无效或缺失收发证据，分别记录ERROR／不可用和缺口，不伪造零吞吐、零丢包或完整性通过。归因仍先区分Core、对端和benchmark；失败本身不改变既定服务端顺序。

## 负载与测量边界

- 1 Gbps是全部流、上下行和两条CN分支合计的应用载荷供给，不是每条流或每方向各1 Gbps，也不是物理接口速率限制。默认64条业务流，纯TCP为32上行／32下行，混合为32 TCP与32 UDP。
- 默认每个UDP源socket轮转64个目标，纯UDP最多4096个逻辑五元组、混合最多2048个；它们不是相同数量的物理代理或QUIC连接。单目标例外以窗口`workload.udp_destinations`为准。
- 额外1000 QPS唯一名称DNS绕过缓存，不计入1 Gbps业务载荷，但会争用CPU和调度。该叠加负载不代表日常场景，也不能只凭最终吞吐把瓶颈归到代理协议。
- 吞吐统计60秒活动窗口内的raw接收，UDP交付丢包包含原收尾预算内收到的有效唯一报文。上下行独立保留，结合已有时间分布识别持续容量不足、单方向问题和突发停滞。
- CPU以进程CPU秒除以业务准备、运行和排空墙时，排除Core最初启动和连通检查、最终Stop；墙时不一定为60秒。100%表示一个逻辑核。生命周期RSS覆盖启动至Stop／reap，与CPU和吞吐的窗口不相同。
- 普通TCP每条流使用起点加63秒的原截止。最后一次写入可能占用收尾预算，期限内缺口是有效FAIL，但不足以证明永久丢失、Core缺陷或FIN错误；有限交付、实际发送前缀与目标配额分开，详见[TCP窗口](tcp-pressure-window.md)。

保留60秒作为容量筛查窗口；单轮结果不宣称长期稳定。小幅改进只对代表组合安排少量重复对照，结合运行波动、实际完成量和综合收益判断，不新增单次改善幅度下限或全矩阵重复门槛。若需寻找容量拐点，在代表失败组合上另选不超过当前1 Gbps范围的较低速率，不重启暂停的2／3 Gbps。DIRECT与原站、服务端和负载器健康用于确认实验设施能够承载输入，不能把设施瓶颈直接归为Core缺陷。

方法参考 TCP 吞吐框架 RFC 6349 与网络设备基准 RFC 2544，仅借鉴窗口、容量与排空的区分，不机械套用设备零丢包判据。

## 结果与后续范围

当前 Linux CLI 1 Gbps 的已接受覆盖及原始 FAIL／ERROR 边界见[最终覆盖结论](../conclusions/full-pressure-final.md)，协议事实见[协议结果](protocol-results.md)，未解决问题见[已知问题](known-issues.md)。分源码有效覆盖不表示所有历史库存均为最终源码 PASS；后续通过不重写旧结果或未知归因。

新的验证仍按单组最多 10 个同一代理协议组合、组内和组间串行编排，每五组或尾批保存结论。公共层变化须显式复验受影响的既有 PASS，包括主清单之外确实受影响的保护项。断点只跳过该批有效通过的精确窗口；性能通过即结束该项性能优化，完整性及其他门禁独立处理。平台、真机、2／3 Gbps、高并发及 Linux system／DHCP 专项继续暂缓。
